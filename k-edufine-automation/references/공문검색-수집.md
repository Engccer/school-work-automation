# 공문 검색·수집과 로컬 접근 차단 진단

2026-10-29 Windows·Playwright MCP 환경에서 확인한 절차. 특정 버전·화면에서 확인한 식별자는 현 화면과 대조한다. 검색·저장 요청은 접수처리·상신·공람 발송을 의미하지 않는다.

## 설치 안내 반복: 미설치와 브라우저 차단 구별

- Playwright와 브라우저가 이미 설치되어 있고 MCP가 작동하면 재설치하지 않는다. 패키지 설치 여부와 현재 도구 연결 상태를 따로 확인한다.
- VeraPort 미설치 표시만으로 재설치하지 않는다. 프로그램 설치 여부·실행 프로세스와 브라우저의 필요한 오류만 확인한다.
- `Permission was denied ... loopback address space`와 `https://127.0.0.1:16106/` 요청 거부가 함께 관찰되면, 사이트가 PC의 VeraPort에 연결하는 요청을 브라우저가 차단한 것이다. 이 증거만으로 Windows 방화벽이나 보안 프로그램 자체의 고장이라고 설명하지 않는다.
- 해당 사이트에 대한 로컬 접근 허용이 승인되어 있고 현재 도구에서 CDP를 사용할 수 있을 때, 아래 방법이 같은 호출 안에서 설치 검사 통과에 성공했다. 기존 승인이 있으면 다시 묻지 않는다. 전체 브라우저·OS 보안 설정을 해제하는 절차로 확대하지 않는다.

```javascript
const cdp = await page.context().newCDPSession(page);
try {
  const { targetInfo } = await cdp.send('Target.getTargetInfo');
  await cdp.send('Browser.grantPermissions', {
    permissions: ['loopbackNetwork', 'localNetworkAccess'],
    origin: 'https://klef.sen.go.kr',
    browserContextId: targetInfo.browserContextId
  });
  await page.reload();
  // 같은 호출 안에서 설치 상태·진입 결과를 확인한다.
} finally {
  await cdp.detach();
}
```

관찰된 한계: 도구 호출 사이 권한이 다시 거부되는 현상이 있었다. 초기화 원인은 미확정이므로 “에이전트와 무관” 또는 “에이전트 설정이 원인”으로 단정하지 않는다. 일반 `context.grantPermissions(['loopback-network'])`는 해당 환경에서 미지원이었고 `Browser.setPermission`도 해결되지 않았다. 같은 실패 호출을 반복하지 말고 실제 권한·화면 결과를 재확인한다.

### 재접속 검증 결과 (2026-10-29)

새 Playwright 연결(처음에는 about:blank 탭만 존재)에서 사용자 인증서 로그인 후, 권한을 변경하지 않고 포털 메뉴로 다시 진입하여 재현했다.

1. 통합설치 프로그램 미설치 alert → 설치 페이지로 이동. `loopback-network=denied`, `local-network-access=prompt`, loopback 접근 거부 콘솔 오류가 함께 확인됐다.
2. 위 CDP 허용 → 새로고침 → 메인페이지 이동을 한 호출에서 실행하면 `loopback-network=granted`, 프로그램 설치됨 표시 7개 및 `main.do` 진입을 확인했다. 본문 전체에는 안내문에도 “미설치”가 있어 단순 문자열 개수로 미설치 프로그램 수를 세면 안 된다.
3. 다음 별도 도구 호출에서 `loopback-network=denied`, `local-network-access=prompt`로 돌아왔지만 이미 열린 메인 화면의 문서관리 메뉴는 존재했다. 따라서 “화면이 유지됨”과 “로컬 접근 허용이 유지됨”은 별개다.

이 조치는 현재 환경에서 **일시적 접속 복구 방법**이며 영구 설정 해결로 보고하지 않는다. Chrome 전체 종료·OS 재부팅 후 시험은 수행하지 않았다. 도구 호출 사이 설정이 초기화되는 구성 요소의 정확한 원인도 아직 확인되지 않았다.

## 문서등록대장 검색

메뉴는 문서관리 → 문서함 → 문서등록대장. 날짜 범위는 사용자의 요청과 현재 날짜로 계산한다. “최근 두 달”을 고정된 달이나 파일 수정일로 바꾸지 않는다.

확인된 업무 프레임과 필드:

```javascript
const frame = page.frames().find(f => f.name().endsWith('.form.webWork_WebBrowser'));
// 화면에서 해당 요소와 조회 함수를 확인한 뒤 사용한다.
// 시작/종료 표시 필드: #basicReportDe, #basicReportDe3
// 내부 날짜 필드: #reportDe, #reportDe3 (YYYYMMDD)
// 제목 표시 필드: #basicSj, 내부: #sj
await frame.locator('#basicSj').fill(keyword);
await frame.evaluate(() => fncSearch(1));
```

- 날짜를 변경한 뒤 표시 값과 내부 값이 의도한 범위인지 확인한다. 표시만 바뀐 검색을 완료로 간주하지 않는다.
- 제목 입력은 `fill()`로 교체한다. 키보드 선택·입력 실패로 검색어가 중복된 사례가 있었다.
- 정상 검색 버튼/Enter가 동작하지 않으면 네이티브 확인창이 가로막고 있는지 확인한다. 화면 소스에서 확인한 조회 함수 `fncSearch(1)`은 읽기 전용 검색 대안이다. 이후 결과 갱신을 기다린다.
- 페이지당 건수 콤보박스는 접근 가능한 이름 `페이지당 건수`, 100건 값은 `100`이었다. 총 결과가 이를 넘으면 `fncSearch(2)` 등 다음 페이지까지 확인한다.
- 예: 사업명 핵심어, `AI`, `디지털`, `결과보고`와 `결과 보고`처럼 표기 차이를 교차 검색한다. 검색어별 건수는 중복 포함이며 서로 합산해 고유 문서 수로 보고하지 않는다.
- 반환 필드는 학교 문서번호·등록일·제목·발신기관·필요 시 원 발신 문서번호로 제한한다. 행 전체의 담당자·계정 정보나 세션 URL은 출력하지 않는다.
- 기존 파일과 대조할 때 폴더 번호보다 연도·학교 접수번호/발신번호를 쓴다. 수정·재발송 문서는 별도 문서로 보존한다.
- “서식을 찾지 못함”은 확인한 날짜·제목·문서함 범위와 함께 보고한다. 검색 결과 부재를 전체 시스템의 부재로 단정하지 않는다. 연간 결과보고·개별 행사 결과·진단검사 결과를 구분한다.

## 외부 앱 열기와 일괄 PC저장

- 제목이나 PC저장 클릭 후 변화가 없으면 Chrome 네이티브의 “WXSClient … 여시겠습니까?” 확인창을 살핀다. Playwright DOM에 나타나지 않을 수 있다. `capture.ps1`로 현재 화면을 확인하고 `click_screen.ps1`로 열기 버튼을 누른다. 예전 좌표를 재사용하지 않는다.
- WXSClient 문서 창 제목이 문서 제목 자체인 경우도 있다. `HCLTAPP_KYUL_` 완전일치만으로 창이 없다고 판단하지 말고 `mshtml_dom.ps1 -ListOnly`로 확인한다. `파일저장` 제목에 제어문자가 붙은 경우에는 부분일치가 유효했다.
- 문서등록대장에서 여러 행을 선택한 뒤 `PC저장`을 사용할 수 있다. `input[name=docinfo]`가 시각적으로 숨겨져 `.check()`가 실패하면 행의 문서번호를 정확히 대조한 후 해당 입력의 `checked`를 설정하는 방법이 동작했다. 선택 문서번호 목록과 실제 선택 건수를 대조하고 PC저장을 누른다. 부분 문자열로 문서번호를 매칭하지 않는다.
- PC저장은 `doCallFileManagerExtra(HCLTAPP_FILESAVE)` 경로로 파일저장 창을 연다. 이후는 [접수처리.md 7단계](접수처리.md)의 옵션 확인 → `fncVerify()` → 폴더 선택 취소 → 경로 패치 확인 → 패치 실행 절차를 따른다. 다운로드만을 위해 `fncProcessDoc()`를 호출하지 않는다.
- 완료 확인은 문서저장 창의 `pMsg`만 읽는다. 폴더 선택을 취소한 기록이 남아 있어도 뒤에 파일별 `ok`와 최종 저장 완료가 있으면 실제 파일을 확인한다. 처음의 취소 메시지만으로 전체 실패라고 판단하지 않는다.
- ASCII 임시 폴더의 파일을 최종 위치에 복사한 뒤, 요청한 문서별 본문·첨부 건수, 0바이트 여부, 가능하면 해시를 대조한다. 종료 메시지만으로 누락 없음을 단정하지 않는다. 첨부 없음도 기록한다.

## 파일 정리와 참조 관리

해당 업무 폴더의 기존 규칙과 사용자의 현재 요청을 우선한다. 다음은 이 환경에서 사용자가 선택한 정리 방식이다.

- 주요 사업 지침·제출 요구 공문: 접수일순 `두 자리 번호. YYYY-MM-DD 제목`.
- 타교 참관 안내·업체 홍보 등 같은 유형의 반복 단순 안내: 번호 없는 `[모음] 유형명` 폴더. 내부에 `YYYY-MM-DD 학교접수번호`별 본문·첨부를 함께 둔다. 단순 안내라는 이유로 원문을 삭제하거나 수정·재발송을 합치지 않는다.
- 접수일이 없으면 발신/등록일 등 확인 가능한 날짜와 근거를 목록에 적는다. 설명회 자료 날짜와 접수일을 구별하고, 날짜를 확인하지 못하면 `일자 미확인`으로 둔다. 파일 생성·수정 시각으로 접수일을 추측하지 않는다.
- 원본은 공문별 폴더, 추출문·요약·스크립트는 별도 작업 하위 폴더. 번호보다 문서번호가 안정적인 식별자이므로 인용 시 함께 기록한다.
- 번호를 바꿀 때 변경 전후 경로표를 만들고 내부 링크·요약·프로젝트 정본 지침도 수정한다. 생성된 지침 파일은 정본에서 동기화한다. 읽기 전용 원본 파일은 이동 전후 목록·크기 또는 해시로 확인한다.
- 폴더명은 등록대장의 제목을 쓰되 길면 식별 가능한 짧은 제목과 접수번호를 쓴다. 본문을 `제목`부터 `1.`까지 잘라 제목으로 삼으면 번호 없는 홍보 문서에서 본문까지 섞인다. 긴 제목은 Windows 경로 길이로 이동·열거 실패를 유발할 수 있으므로 최종 파일 경로까지 확인한다.
- Windows에서는 검증된 절대 경로를 같은 PowerShell 세션에서 `Move-Item -LiteralPath`로 처리한다. `$ErrorActionPreference='Stop'` 등으로 이동 실패 뒤 성공 메시지가 나오는 것을 막는다. Windows PowerShell 5.1은 BOM 없는 UTF-8 한글 스크립트를 오독할 수 있으므로 UTF-8 BOM으로 저장하거나 PowerShell 7을 사용한다.

## MSHTML 문자열 전달 오류와 진단 출력

`mshtml_dom.ps1`의 script 요소 `text` 속성에 `Get-Content` 결과를 그대로 넘기면 “문자열이 필요합니다”/COM `0x80020101` 오류가 발생한 환경이 있었다. `Set-DomProp $el "text" ([string]$code)`로 명시적 문자열 변환한 사본에서 주입·저장에 성공하여 정본에 반영했다.

진단 시 전체 `document.body.innerText`를 무조건 출력하지 않는다. MSHTML 문서에는 스크립트 소스·토큰 등이 함께 섞일 수 있다. 옵션의 체크 상태, 필요한 본문 필드, `pMsg` 같은 최소 필드만 조회한다. 브라우저 콘솔·네트워크 로그도 전체 출력 대신 관련 오류만 추린다. 도구가 자동 생성한 세션 로그·화면 파일은 작업 후 자신이 생성한 파일임을 확인해 정리한다.
